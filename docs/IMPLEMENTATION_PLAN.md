# План реализации для двух backend-разработчиков

Это целевой план, а не отчёт о готовом коде. Обозначения AO ниже — локальные идентификаторы задач, не номера GitHub Issues.

## Правила

На задачу — один автор, второй участник — ревьюер. Каждый автор реализует код, тесты и документацию своей части. Направления меняются между этапами, чтобы оба получили опыт API, SQL и фоновой обработки.

Зависимости задают порядок. Не начинаем SDK и граф до согласования контракта. Интеграционные тесты появляются вместе со сценарием, а не в конце проекта.

## Первые две итерации

**Итерация 1:** вместе согласовать AO-01. Один участник берёт AO-02, второй готовит fixtures и API examples AO-01. После основы — AO-03 и затем AO-04. Итог: HTTP → PostgreSQL → GET, подтверждённый интеграционным тестом.

**Итерация 2:** автор Projects/Runs берёт SDK (AO-06), автор ingestion — запросы (AO-05). Затем совместно проверяют дубли и отказ Collector. Сроки определяем после первой итерации по реальному темпу.

## Демонстрация на собеседовании

1. Запустить Compose и sample.
2. Показать Run с двумя параллельными агентами, model/tool calls, ошибкой и retry.
3. Повторно отправить batch и показать отсутствие дублей.
4. Остановить Collector: sample продолжает работать; показать результат восстановления и ограничения очереди.
5. Открыть завершённый Run после перезапуска backend.
6. Показать интеграционный тест, индекс и explain, CI и один PR с review.

В README релиза фиксируем измеренные результаты и условия теста. Не заявляем гарантированную доставку, highload или overhead без измерений.

## Старые GitHub Issues

Issue #4 и старые назначения отражают предыдущую схему команды. Закрытые duplicate Issues не являются выполненными этапами. До начала очередной задачи выбираем один соответствующий открытый Issue, обновляем scope и assignee по этому плану, а ссылку добавляем сюда. Если подходящего нет, создаём новый. Историю не удаляем.
