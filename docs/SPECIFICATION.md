# Техническое задание

## 1. Назначение

Agent Observatory — система мониторинга, визуализации и анализа выполнения программных агентных систем.

Система подключается к существующему приложению и получает структурированную телеметрию выполнения. Agent Observatory не выполняет роль агента и не вмешивается в принятие решений наблюдаемой системой.

## 2. Цели

Система должна позволять:

1. фиксировать отдельные запуски (Run);
2. отслеживать агентов и подагентов;
3. регистрировать вызовы моделей;
4. регистрировать вызовы инструментов;
5. фиксировать ошибки, таймауты и повторные попытки;
6. измерять длительность операций;
7. учитывать объём использования моделей;
8. отображать процесс выполнения в виде графа;
9. отображать процесс во временной шкале;
10. искать и фильтровать события;
11. просматривать завершённые запуски;
12. обеспечивать минимальное влияние мониторинга на наблюдаемое приложение.

## 3. Основные сущности

```text
Project
└── Run
    ├── Agent
    │   ├── ModelCall
    │   ├── ToolCall
    │   ├── Error
    │   └── Retry
    └── SubAgent
```

Базовое событие содержит:

- EventId
- RunId
- AgentId
- ParentId
- Timestamp
- Type
- Status
- Duration
- Metadata

## 4. Интеграция

### 4.1 .NET SDK

SDK предоставляет API для регистрации Run, Agent, ModelCall, ToolCall, Error и Retry.

### 4.2 HTTP API

Для любых языков и сред должен существовать прямой HTTP API приёма событий.

### 4.3 OpenTelemetry

После MVP планируется поддержка OpenTelemetry/OTLP как стандартного транспорта телеметрии.

## 5. Требования к производительности интеграции

- события помещаются во внутреннюю очередь;
- отправка выполняется в фоне;
- поддерживается пакетная отправка;
- сбой Collector не должен останавливать наблюдаемое приложение;
- мониторинг не должен требовать дополнительных запросов к модели;
- чувствительные данные должны иметь возможность не сохраняться.

## 6. Функции MVP

- создание и просмотр проектов;
- создание, завершение и просмотр Run;
- HTTP ingestion API;
- .NET SDK;
- асинхронный exporter;
- PostgreSQL;
- realtime-доставка событий в UI;
- список Run;
- карточка Run;
- execution graph;
- timeline;
- просмотр model calls;
- просмотр tool calls;
- ошибки и retries;
- статистика длительности и использования модели;
- поиск и фильтрация.

## 7. Нефункциональные требования

- backend должен работать локально;
- API не должен зависеть от конкретной агентной среды;
- порядок событий должен сохраняться;
- должна поддерживаться параллельная работа нескольких агентов;
- недоступность Agent Observatory не должна нарушать выполнение наблюдаемого приложения;
- телеметрия должна иметь настраиваемый уровень детализации.

## 8. Критерий готовности MVP

MVP считается готовым, если тестовая агентная система:

1. создаёт Run;
2. создаёт одного или нескольких агентов;
3. регистрирует вызовы модели и инструментов;
4. регистрирует ошибку и повторную попытку;
5. передаёт события в Agent Observatory;
6. события сохраняются;
7. UI обновляется в реальном времени;
8. пользователь видит execution graph и timeline;
9. завершённый Run можно открыть позднее.

## 9. Ограничения MVP

В MVP не входят:

- собственная агентная среда;
- глубокое профилирование ОС;
- поддержка всех языков и фреймворков;
- автоматическое исправление проблем;
- сложная распределённая инфраструктура хранения;
- обязательная поддержка OpenTelemetry.

## 10. Перспективы

- OpenTelemetry/OTLP;
- SDK для других языков;
- адаптеры к популярным агентным средам;
- сравнение Run;
- regression analysis;
- автоматическое обнаружение аномалий;
- автоматизированная диагностика;
- CI/CD интеграция;
- командный серверный режим.
